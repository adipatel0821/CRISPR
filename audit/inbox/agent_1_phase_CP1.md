**Milestone 1 (CP1 engine), commit 70982bb.** The engine is pure Decimal functions with a 28-digit context and ROUND_HALF_UP.
- **F00 principal resolution:** stated principal → AF + PFC ("derived") → AF alone with a_pfc_zero and flag PFC_ASSUMED_ZERO ("assumed_pfc_zero") → a new itemization path ("derived", the reason is written into `metrics.principal.notes`). If only the APR is given, it is used as the rate, with assumption a_rate_from_apr and a warning.
- **Loan formulas:** payment and schedule on the principal (F01/F01s, final payment absorbs the cent residue); TOP (F02); finance charge = TOP − AF (F03); interest = TOP − principal (F03i); total paid through the deal with the breakdown (F04); APR by bisection on [0,2] over the actual schedule payments (F05).
- **Ratios and transaction effects:** LTV and negative equity at start (F06/F06d), payment/take-home (F07), DTI on debts_after (F07b), F08/F09 with the flexible-spending label rule, F13, F14 (unknown new-car costs → 0 with the label "new-car running costs not included" and assumption a_no_running_costs), reserve months (F10b/F10), savings months of income (F11), and the equity timeline F12 from user estimates only.
- **Flags v1.1:** citations come from config; "CFPB median" appears nowhere.
- **Other pieces:** `offer_checks` → OfferCheckReport (payment mismatch, arithmetic identities, warn-only APR recompute, itemization, range, unsupported features); `month_net` / `month_components`; `load_config` / `assumptions_payload`; `config/assumptions.yaml`.
- **Status rules:** missing inputs give `{value: null, status: "missing", missing_inputs}`, never zero. Results carry the weakest status and verification of their inputs, and self-reported facts always give verification "none".
- **IDs:** `calc_id` is a hash of the inputs, so the same inputs give the same id.

**Milestone 2 (scenarios), commit 538c07a.** `run_catalog` runs the catalog from `config/scenarios.yaml` (horizon 12, seed 20261024 recorded). Each scenario runs twice: without the offer (starting from savings) and with it (starting from F13 savings after purchase). Every month goes through `engine.month_components`. Savings are floored at 0 and any shortfall builds an unfunded gap that later surpluses repay first. Each result reports runway, max gap, recovery month, savings at the end and deficit at baseline. Every scenario assumption text starts with "Illustrative". `ResilienceSummary` gives break_even_m3 and break_even_m6 as an exact closed form (the minimum over months of (S0 + cumulative net) / cumulative income), rounded down to 2 dp, with the deficit and capped edge cases. If stress_test is not ready it returns `([], None)`.

**Milestone 3 (counterfactuals), commit 21dee4b.** `evaluate` runs every alternative through `engine.compute` on a changed offer/facts, plus the scenario break-even.
- **Cash down lever:** bounded by savings after purchase. If the down payment source is not savings, the extra is taken from savings and the alternative is flagged extra_down_from_savings.
- **Term and add-on levers:** any term different from the offer carries same_rate_assumed. Only add-ons with optional == True are ever removed.
- **Competing offers:** only offers with `ready_for_calculation`.
- **Base alternative and outputs:** the base alternative is byte-equal to the base calculation. Output includes the four objectives, the Pareto set, a rate-sensitivity statement (+1 point → payment +9.20, as a statement and not an offer), the one-at-a-time sensitivity ranking, notes and deferred levers. No APR is invented.

**Hardening, commit e65f599.** If savings after purchase are negative (cash at signing exceeds reported savings), scenarios start with an unfunded gap instead of a negative balance, and compute adds a warning.

**Measured performance** (reference case, Windows): compute 2.3 ms, baseline compute 0.6 ms, run_catalog 5.2 ms, evaluate 33 ms for a 16-alternative grid and about 0.1 s for 32 alternatives. Targets were < 5 ms and < 1.5 s.

Assumptions:
- The equity timeline (F12) turns date-based value estimates into loan months relative to `as_of`, which defaults to the computation date. Results that include date-based estimates are therefore not byte-reproducible across days. Month-indexed estimates ({"month": 12, ...}) are fully deterministic. There is no loan start date in the contracts.
- If `cash_down` is absent from an offer and the down payment source is not 'none', total paid through the deal (F04) and savings after purchase (F13) are reported as missing (offer.cash_down). A missing trade-in value or payoff is treated as no trade-in, and a missing pfc_paid_in_cash as 0, meaning the prepaid charges are in the note per F00. Both choices are noted in code.
- The PREPAYMENT_PENALTY flag reports triggered=false with detail 'Not stated in the offer.' when the term is absent. Flag has no status field, so 'unknown' cannot be expressed any other way.
- The sc_cost_rise scenario adds 20% of |F14|, so costs always go up even when F14 is negative. When new-car costs are unknown, F14 = 0 and the scenario changes nothing.
- The break-even is solved in closed form, which is mathematically equal to the bisection in the stage doc, and rounded DOWN to 2 dp so a sustainable fraction is never overstated. This is a deliberate exception to ROUND_HALF_UP. ResilienceSummary.capped refers to M=3.
- derived_status counts only loan-math assumptions (a_pfc_zero, a_rate_from_apr) as 'assumed'. Leaving out new-car running costs (a_no_running_costs) is disclosed through the label and assumptions_used and does not downgrade the status.
- The extra fields Metric.notes and Metric.points are not in the exported JSON schema or TS types (Metric is extra='allow').
- Integration is untested: compute/run_catalog/evaluate have only been exercised against my own fakes and fixtures, not against Agent 2's real ledger facts or LoanOffer objects, nor Agent 4's API orchestration.
