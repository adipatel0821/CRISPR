M1, adaptive intake (commit b3b6c8e):
- config/ontology.yaml (ontology_version "1.1"): every canonical key, plus debt item fields matched by the pattern debts[id].field. Each entry has value_type, unit, validators, dependency_order (take-home 10, essentials 20, debts.count 30, debt payment 31, savings 40, down-payment source 45, low month 50; refinements 60-70), a question template and plain-language "why" text.
- config/question_policy.yaml: the curated refinement order.
- intake/ontology.py: builds a NetworkX graph whose fact -> metric -> analysis edges are generated from engine.requirements REQUIRED_INPUTS and ANALYSIS_METRICS. Two conditions come from ontology metadata: the down-payment source is not required when cash down is 0, and the low month is required for stress_test when income varies. Also provides graph_readiness (used for the A-23 parity test) and export_nodes / export_edges.
- intake/ledger.py: append-only ledger with typed normalization (currency to 2 dp with ROUND_HALF_UP and >= 0, integers with ranges, enums by value or label, booleans, a JSON list of value estimates). Supports statuses provided / estimated / declined; changes create a new fact that supersedes the old one. Unknown keys raise FactValidationError with an actionable message. When debts.count = N, it adds explicit "missing" payment facts for d1..dN. Also current_facts and retract.
- intake/rules.py: H01_deficit (asked once, never a conflict), H02_savings_high, H02_down_payment, and C01 re-validation.
- intake/questions.py: next_question uses engine.requirements.evaluate_all for readiness. Order is pending acknowledgements first, then missing blockers of unavailable selected analyses sorted by (dependency_order, item index, key), then question=None plus refinements. The flexible-spending refinement_effect comes from a lazily imported engine.compute(facts, None) and is left out if the engine is unavailable. Question ids are deterministic (q_<key>, q_ack_<rule>). Also apply_answer (typed parse, declined, skipped, estimate, acknowledgements) and candidate_from_id.
- Persona P2: a range answer to take-home ("2,800 to 4,000") records income.variability = somewhat_variable. The next question is a currency_pair asking for a typical month and a slow month.

M2, manual offer (commit 2e12679):
- documents/manual.py build_manual_offer, built on shared documents/terms.py so manual entry and extraction run the same checks.
- Rates must be fractions below 1; "4.75" is rejected with "enter the rate as a fraction, e.g. 0.0475". "4.75%" with an explicit % sign is accepted as 0.0475. term_months must be 6-96.
- Each term is user_input / provided, verification user_confirmed or none, with evidence labelled "You entered".
- variable_rate true or balloon > 0 raises UnsupportedProduct, which carries the draft offer.
- engine.offer_checks is imported lazily and its results fill per-term checks, derived values (principal_basis, trade_in_equity, negative_equity_rolled_in) and warnings. PAYMENT_MISMATCH is added when the gap exceeds $1.
- ready_for_calculation follows the minimum computable set.

M3, LLM and documents (commit dd8290a):
- llm/client.py LLMClient with LLM_DATA_MODE enforced inside the client: off never sends anything, synthetic_only sends only fixture-flagged content, paid sends anything; paid is never enabled automatically and an unknown value falls back to synthetic_only. Redacts SSN, email, phone, account and card numbers before any call. 25 s timeout, structured output through response_schema, one retry then LLMMalformedOutput. Logs carry only a prompt hash, latency and outcome. Factory: get_llm_client().
- scripts/make_fixture_pdfs.py writes 7 reproducible SYNTHETIC PDFs plus manifest.json (SHA-256 and ground truth per file); all are committed. The fixtures are: standard reference contract, two-option worksheet (60 and 72 months), blank APR, variable rate, balloon, prompt injection, and "No balloon" with a fake SSN.
- documents/tila_reader.py: deterministic reader for the five box fields, payment schedule, principal, prepaid finance charge, contract rate, price, taxes and down payment. Detects multiple offer columns, handles negation for variable-rate and balloon wording, and screens out instruction-like lines.
- documents/pipeline.py process_document: magic-byte check (PNG/JPG rejected with "Scanned images are not supported yet; enter the terms manually."), 10 MB and 30-page limits, encrypted or corrupt PDF rejected, synthetic_only plus a non-fixture raises DataModeRestricted. Text comes from PyMuPDF. The LLM is used only when the client allows; otherwise extraction is reader-only.
- The verifier runs quote_match (rapidfuzz, threshold 90), label_anchor (120-character window) and the independent reader; a disagreement sets status conflicting with both values in alternatives_found. Engine checks are added afterwards. More than one offer gives status needs_choice. The draft offer is never ready_for_calculation.
- documents/verify.py apply_verification: applies offer_choice and confirm / correct / reject. evidence_matched_user_confirmed only when the evidence matched and the user confirmed; a corrected value becomes user_input / user_confirmed. The offer becomes ready only after the minimum-set terms are confirmed or corrected.
