Affected files: backend/engine/requirements.py (_cash_down, required_facts lines 135-158)
Finding:
The down-payment-source condition drops `loan.down_payment_source` in two cases where F13 still needs it:
(a) cash_down = 0 but `pfc_paid_in_cash` > 0. F13 (stage_03 §11) = `savings − (CD if source = savings) − (PFC_paid_in_cash if source = savings)`, so savings_after_purchase, F10 and F11 still depend on the source.
(b) The cash_down term has value "0.00" but status `conflicting` (or any status that is not provided, estimated or calculated). `_cash_down` reads the value without checking the status, so an unverified or disputed 0 removes a blocking requirement. That contradicts contracts §6.1 ("missing, declined and conflicting never enter as numbers").
Evidence:
audit/evidence/probe_cp0_output.txt:
  [cash_down=0, pfc_paid_in_cash=500] -> required has no 'loan.down_payment_source'
  [cash_down=0.00 but status conflicting] -> required has no 'loan.down_payment_source'
  (control) [cash_down=4000] -> 'loan.down_payment_source' required
Required correction:
Require `loan.down_payment_source` unless the offer has cash_down = 0 with a computable status (provided, estimated or calculated) AND pfc_paid_in_cash is known to be 0 or is absent. Put another way, require it when cash down + PFC paid in cash > 0, or when either value is unknown or disputed. Read term values only when their status is computable.
Done when:
Both probe cases above list loan.down_payment_source as required, and as missing when the fact is absent. A provided cash_down "0.00" with no pfc_paid_in_cash still omits it.
Verification test:
pytest with three offers: (1) cash_down 0 + pfc_paid_in_cash 500 → required_facts("reserve_impact", ...) contains "loan.down_payment_source"; (2) cash_down 0 with status conflicting → contains it; (3) cash_down 0 provided with no PFC in cash → omits it. Agent 5 re-runs audit/evidence/probe_cp0.py.
Status: OPEN
END DIRECTIVE
