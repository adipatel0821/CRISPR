Finding:
When an assumption substitutes a value, the result's provenance still says "provided". This breaks contracts §1.3 ("A calculated value carries derived_status = the weakest input status (provided > estimated > assumed)").
When new-car running costs are unknown, `incremental_vehicle_costs` returns `Derived(value=0, assumptions=("a_no_running_costs",))` with no status entry. The `a_not_replacing` branch has the same gap: its assumption is recorded but no "assumed" status is added. compute() builds `derived_status` only from statuses, so F14, F09 (monthly_left_after), F10 (reserve_months_after) and the CalculationResult as a whole report `derived_status = "provided"`, even though their value depends on a $0 assumption.
The loan path does this correctly: loan_payment_basis appends "assumed" for a_pfc_zero and a_rate_from_apr. Only the F14 path is inconsistent.
This is visible in the product. The default demo path skips new-car costs (the live walkthrough's dashboard shows F09 $924.86 computed with F14 = $0), and the result is labelled as provided-quality data. That undercuts the trust and label-honesty claim the submission rests on.
Secondary: when `vehicle.replaces_current = true`, essentials still contain the current car's costs. F14 = 0 therefore really assumes the new car costs the same as the current one, not that running costs are "not included" as the label says.
Evidence:
audit/evidence/cp1_audit/engine_audit_cp1_output.txt, "Missing-value handling":
  no new-car costs -> F14='0.00' label='new-car running costs not included' assumptions_used=['a_no_running_costs'] derived_status='provided' F09='524.86'
Compare the engine's own a_pfc_zero path, where loan_payment_basis appends "assumed" (backend/engine/transaction.py, lines 26-36).
Required correction:
In incremental_vehicle_costs, give every assumption-substituted Derived `statuses=("assumed",)`. This covers a_no_running_costs, and a_not_replacing where new costs are known but replacement is unknown. weakest_status then propagates to F14, F09, F10, F11-after and derived_status. Optionally make the label precise when replaces_current is true, for example "assumes the new car costs the same to run as your current one".
Done when:
